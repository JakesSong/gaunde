# 가운데

모임 중간 지점 찾기. 수도권 전철 기준으로 **"제일 오래 걸리는 사람이 가장 덜 억울한 역"** 을 찾아준다.

가입 없음. 모임 링크의 토큰이 곧 접근 권한이다.

1. 주최자가 모임 이름을 적으면 공유 링크가 나온다.
2. 참여자는 링크로 들어와 이름과 출발역만 고른다.
3. 전원의 소요시간 중 **최댓값이 최소가 되는 역**(minimax, 동점이면 소요시간 합계로 tie-break)을 제시한다.

소요시간은 외부 실시간 API가 아니라 **직접 만든 수도권 전철 그래프 위에서 다익스트라로 계산**한다.

---

## 빠르게 돌려보기

```bash
npm install
npm run build:graph     # data/raw/* -> data/graph.json
npm test                # 알고리즘·데이터·현실 대조 22개
npm start               # http://localhost:3000
```

DB 설정이 없으면 로컬 SQLite(`data/gaunde.db`)를 쓴다. `DATABASE_URL` 이 있으면 PostgreSQL 로 붙는다.

end-to-end 검증(헤드리스 jsdom 으로 실제 화면 흐름을 그대로 밟는다):

```bash
npm start &
node test/e2e.mjs
```

### 소요시간 모델

실측 268개 구간에 최소제곱 적합:

```
t_run(초) = (24.3 + 62.8 × km) × speedFactor[노선]
```

- **적합 오차 MAE 11초**, 95%가 30초 이내. 도시철도 기준 순항속도 약 57 km/h.
- **경로계수 1.044** — 직선거리를 선로거리로 바꾸는 보정. 실측 역간거리 ÷ 직선거리의 평균.
- **정차시간 30초/역** — 별도로 더한다. 공표 소요시간에는 정차시간이 포함되고 위 실측값에는 빠져 있다는 걸
  2호선 순환(주행 합 65분 vs 공표 87분, 43개 정차)에서 확인해 산출했다.
- **speedFactor** — 광역철도·급행형은 도시철도보다 빠르다. 공표 전구간 소요시간에 맞춰 보정했다
  (`scripts/calibrate-speed.mjs`, 고정점 수렴까지 반복).

| 노선 | 배율 | 맞춘 기준점 | 결과 |
|---|--:|---|---|
| 경춘선 | 0.649 | 청량리→춘천 82분 | 82.0분 |
| 경의중앙선 | 0.934 | 문산→용문 165분 | 165.0분 |
| 공항철도 | 0.779 | 서울역→인천공항1터미널 59분 | 59.0분 |
| 신분당선 | 0.792 | 신사→광교 42분 | 42.0분 |
| GTX-A | 0.342 | 운정중앙→서울역 22분 | 22.1분 |
| 기타 광역철도 | 0.792 | (위 두 기준점의 평균) | |
| 도시철도·경전철 | 1.000 | (적합식 자체가 이 기준) | |

**환승** — 도보 150초 + 환승할 노선 배차간격 ÷ 2. 최초 승차에도 배차간격 ÷ 2 를 더한다.
배차간격은 평일 낮 대표값 추정치다(`LINES` 의 `headwayMin`).

### 손본 곳 (전부 `build-report.json` 에 기록)

- OSM 공항철도 홍대입구·디지털미디어시티 승강장에 `name` 태그가 없어 그냥 두면 **공덕→마곡나루 가짜 지름길**이
  생긴다. 최근접 역명(59m·148m)으로 해석해 붙였다.
- 우이신설선 삼양사거리 정거장이 `삼양` 으로 오태깅되어 삼양역이 둘로 갈라져 있었다. 좌표로 확인해 바로잡았다.
- 서울교통공사 CSV 의 `당고개` 는 2024-08 개명된 `불암산` 으로 옮겨 매칭했다.
- 급행·특급·직통 계통 관계 30개는 각역정차 기준을 지키기 위해 제외했다.
- 동명이역은 이름이 같아도 450m 넘게 떨어져 있으면 분리한다 — 5호선 양평 ↔ 경의중앙선 양평,
  2호선 신촌 ↔ 경의중앙선 신촌.

### 알려진 한계

- **1호선 경부/경인/경원 계통, 2호선 지선, 5호선 마천지선을 한 노선으로 본다.** 계통이 갈리는 곳(구로·성수·강동 등)
  에서 실제로는 열차를 갈아타야 하는데 그 대기시간이 빠진다.
- **급행을 쓰지 않는다.** 각역정차 기준이라 급행이 있는 구간은 실제보다 느리게 나온다.
- **GTX-A 성남역이 OSM 관계에 없다.** 수서~구성 사이 정차가 빠져 있다.
- **배차간격이 시간대별로 바뀌지 않는다.** 평일 낮 기준 고정값이다.
- 추정 구간은 직선거리 기반이라 곡선 구간에서 과소평가될 수 있다.

## 2. 알고리즘

정점은 **(역, 노선) 승강장**이다. 같은 역이라도 노선이 다르면 다른 정점이라 환승 비용이 정확히 붙는다.
658개 역 → 정점 780여 개.

간선 비용(초):

| | |
|---|---|
| 승차 | 구간 주행시간 + 정차 30초 |
| 환승 | 도보 150초 + 배차 ÷ 2 − 정차 30초 (내릴 때는 문 닫힘을 안 기다리므로) |
| 최초 승차 | 배차 ÷ 2 |
| 도착 | 마지막 정차 30초는 체감하지 않으므로 총합에서 1회 차감 |

이렇게 두면 모든 간선 비용이 음이 아니라 다익스트라가 성립한다.

**중간지점 선택** — 참여자마다 다익스트라를 한 번 돌려 전 역까지의 소요시간을 얻고,
후보 역별로 `max(참여자 소요시간)` 이 최소인 역을 고른다. 동점이면 합계가 작은 쪽.

### 검증 (`npm test`, 22개 통과)

- **알고리즘** — 다익스트라를 벨만-포드와 전 정점 대조(출발역 3곳). minimax 를 완전탐색과 대조.
  복원한 경로의 구간 합 = 총 소요시간. 동점 tie-break 순서. 최적해 ≤ "누군가의 집 앞".
- **데이터** — 658개 역 전부 서울역에서 도달 가능(고립역 0). 주요 환승역 10곳의 노선 구성.
  동명이역 분리. 같은 노선 내 역명 중복 없음.
- **현실 대조** — 보정에 쓰지 않은 8개 구간을 실제 통행시간과 ±25% 이내로 대조.
  2호선 사례는 구간 주행시간이 전부 실측값이라 사실상 산술 검산이다.

## 3. 구성

```
scripts/build-graph.mjs     원본 -> data/graph.json  (재현 가능한 단일 파이프라인)
scripts/calibrate-speed.mjs 공표 소요시간에 speedFactor 를 맞추는 보정기
server/graph.mjs            그래프·다익스트라·minimax  (의존성 없음)
server/db.mjs               저장소 (DATABASE_URL 있으면 Postgres, 없으면 SQLite)
server/index.mjs            Express API
public/                     프런트 (목업 디자인 계승, 빌드 도구 없음)
test/graph.test.mjs         단위·통합 테스트
test/e2e.mjs                헤드리스 end-to-end
supabase/schema.sql         Postgres 스키마 + RLS
render.yaml                 Render Blueprint
```

### API

| | |
|---|---|
| `GET /api/health` | 상태 |
| `GET /api/meta` | 데이터 출처·커버리지·모델 계수 |
| `GET /api/stations` | 역 목록 (자동완성용) |
| `POST /api/meetings` | 모임 생성 → 토큰 발급 |
| `GET /api/meetings/:token` | 모임 + 참여현황 |
| `POST /api/meetings/:token/participants` | 출발역 등록 (같은 이름이면 덮어쓰기) |
| `DELETE /api/meetings/:token/participants/:id` | 참여 취소 |
| `GET /api/meetings/:token/result` | 중간지점 계산 |
| `POST /api/track` | 프런트에서만 아는 이벤트 수집 (fire-and-forget, 항상 204) |
| `GET /api/stats` | KPI·퍼널 집계 |

## 5. 측정

**KPI = 생성된 링크 중 참여자 3명 이상 모인 비율 (목표 30%)**

외부 분석 도구 없이 `events` 테이블에만 쌓는다. 테이블은 서버 부팅 시 자동 생성되므로
Supabase 에서 SQL 을 따로 돌릴 필요가 없다.

| 이벤트 | 기록 지점 | 용도 |
|---|---|---|
| `room_created` | `POST /api/meetings` (서버) | KPI 분모 |
| `origin_submitted` | `POST /api/meetings/:token/participants` (서버) | 참여자 수 |
| `result_viewed` | `GET /api/meetings/:token/result` 성공 시 (서버) | 완주율 |
| `share_clicked` | 결과 화면 공유 버튼 → `POST /api/track` (프런트) | 의도 |

남기는 건 무슨 일이 언제 어느 모임에서 일어났는지 뿐이다.
**IP·User-Agent·쿠키·기기 식별자는 저장하지 않고**, `meta` 에도 역 이름과 카운트만 들어간다
(참여자 이름은 `participants` 에 이미 있고 집계에 쓸 일이 없어 넣지 않는다).

```bash
curl -s https://<주소>/api/stats | jq .kpi
```

`events` 는 이벤트 총계, `funnel` 은 모임 중복을 제거한 단계별 수를 낸다
(결과 화면은 새로고침하면 또 기록되므로 총계는 부풀 수 있다).
